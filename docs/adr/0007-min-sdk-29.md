# ADR 0007 — `minSdk = 29` to match Quest 2's first API level

- **Status**: Accepted
- **Date**: 2026-11-07

## Context

Android's `minSdk` tells Android which devices CAN install the app. Too low means we can't use modern APIs without guarding. Too high excludes devices we'd otherwise support.

We reverse-engineered the Quest 2 OTA and found:

- `ro.product.first_api_level = 29` on Quest 2 (= Android 10).
- Current userdevice: Android 14 (SDK 34), HorizonOS branch `releases-oculus-14.0-v209`.
- Quest Pro / Quest 3 / Quest 3S all run Android 14 base too.

## Decision

- `minSdk = 29` (matching Quest 2's first API level).
- `targetSdk = 35` (Android 15; required for `core-ktx:1.15.0` which we use).
- `compileSdk = 35` (same).

## Rationale

- minSdk 29 covers every Quest ever made that runs modern HorizonOS.
- minSdk 29 covers ~98% of Android devices in the wild, so we don't lose non-Quest users who might want the app on a regular Android tablet.
- Dropping to 24 or lower would gain nothing (no earlier Quest supports HorizonOS anyway) and cost us the deprecations.
- Going higher than 29 would exclude Quest 2 users whose device still reports `first_api_level=29`.

## Consequences

- +: we can freely use anything from API 29 (notification channels, scoped storage, wi-fi suggestion API, the works).
- +: no `@TargetApi` guards for the common case.
- -: API 29+ shuns some older patterns (scoped storage, implicit broadcast limits). We don't do anything that trips on this.

## When to revisit

- If a user reports they're on a Quest-1-era HorizonOS that's still API 28 or lower (very unlikely — Quest 1 is end-of-life).
- When `targetSdk` bumps become non-trivial (core-ktx and friends will push us to 36, 37 over time).
